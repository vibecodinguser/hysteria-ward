# Домен панели: сервер или отдельный поддомен

**Статус:** принято

Сейчас панель всегда живёт на `panel.<домен>`, а установщик спрашивает только домен сервера. Нужно дать
администратору выбор: оставить панель на домене сервера или вынести её на отдельный поддомен. Выбор не должен
ломать существующие установки и не должен требовать второго сертификата.

**Почему не как у внешней панели.** У внешнего продукта есть режим с отдельным `PANEL_DOMAIN`: Caddy слушает
443/TCP, по SNI разводит домен прокси и домен панели, а панель проксирует на `127.0.0.1:3000`. В Hysteria Ward
раскладка другая: ядро занимает UDP 443, панель — отдельный TCP 8443. Разводить SNI не нужно, второй веб-сервер
не нужен, а Caddy добавил бы ещё одну службу и второй источник сертификатов. Поэтому внешняя схема не
копируется: остаются те же два слушателя, что и сейчас.

**Два режима.** `server` — панель открывается по домену сервера; сертификат выписывается на одно имя. Это
режим для SSH-туннеля: снаружи панель не слушает, а домен нужен только для SNI и сертификата. `subdomain` —
панель открывается по отдельному имени; по умолчанию `panel.<домен>`, но администратор может указать другое имя
в том же базовом домене. Сертификат выписывается на два имени. Режим по умолчанию — `subdomain`: так панель
работала до этого решения, и существующие установки не меняют адрес. Исключение — домен сервера, который сам
начинается с `panel.`: для него умолчание `server`, иначе новый адрес стал бы `panel.panel.<домен>`.

Публичная панель не может жить на домене сервера: домен сервера остаётся именем, по которому клиенты
подключаются к ядру, и не должен одновременно быть входом в панель. Поэтому `access=public` требует
`subdomain`, а `server` допустим только с `tunnel`.

**Один сертификат.** Имена сертификата собираются из домена сервера и домена панели, дубликаты убираются. В
режиме `server` имя одно, в режиме `subdomain` — два. Отдельный сертификат для панели не заводится: клиенты
Hysteria сверяют `pinSHA256` с тем же сертификатом, который предъявляет ядро. Второй сертификат сломал бы это
соответствие и добавил бы вторую учётную запись ACME.

**Хранение.** В `PanelSettings` рядом с `Access` и `Port` появляются `Mode` (`server` или `subdomain`) и
`Domain`. Пустой `Domain` — не «домена нет», а «взять `panel.<домен>`»: значение по умолчанию не записывается,
поэтому смена домена сервера переносит и панель. Явно заданный домен панели остаётся прежним.

Миграция не нужна. В старой базе полей `Mode` и `Domain` нет: такая запись эффективно читается как `subdomain`
с пустым `Domain`, то есть как `panel.<домен>`. Исключение — старый домен сервера, который сам начинается с
`panel.`: его эффективный режим — `server`. Иначе прежнее поведение `certs.Hosts` превратилось бы в
`panel.panel.example.com`. Новый установщик пишет режим явно, поэтому это исключение действует только для
старых записей. Старая публичная панель на домене `panel.*` тоже продолжает работать: это единственная
допустимая пара «публичная панель на домене сервера», и она распознаётся по пустому `Mode`.

**Разрешение имени.** `PanelSettings.Host(доменСервера)` возвращает домен панели: в режиме `server` — домен
сервера, в режиме `subdomain` — явный `Domain` или `panel.<доменСервера>`. `PanelSettings.Hosts(доменСервера)`
возвращает уникальные имена сертификата в порядке «сервер, панель». Пакет `certs` больше не угадывает `panel.`:
имена приходят из настроек, а он только выпускает сертификат на готовый список.

**Проверки.** Домен панели — валидное DNS-имя без схемы, пути и порта; IP-адрес не принимается, потому что для
него не выписать ACME-сертификат. В режиме `subdomain` домен панели обязан отличаться от домена сервера и
находиться в том же registrable domain: `example.com`, `vpn.example.com` и `panel.example.com` — один базовый
домен, `admin.other.com` — уже другой. Проверка идёт через `golang.org/x/net/publicsuffix`
(`EffectiveTLDPlusOne`), а не по последним двум меткам: иначе `example.co.uk` развалился бы на `co.uk`. В
режиме `server` поле `Domain` должно быть пустым; публичный доступ в этом режиме запрещён. Для старого домена
сервера, записанного как IP-адрес, проверка базового домена пропускается: у IP его нет, и ломать такую
установку обновлением нельзя.

Проверка стоит в `ValidateInitialSetup` и при смене домена сервера. `PanelSettings()` проверяет пару при чтении:
испорченная база не должна молча поднять публичную панель на домене сервера. Смена домена сервера работает так:

- `server` — панель переезжает на новый домен;
- `subdomain` с пустым `Domain` — домен панели пересчитывается как `panel.<новый домен>`;
- `subdomain` с явным `Domain` — домен панели остаётся прежним; если он вне базового домена нового сервера,
  смена отклоняется с объяснением.

Менять режим или домен панели после установки в этом объёме нельзя: интерфейс показывает домен только для
чтения. Модель хранения уже позволяет добавить отдельную команду позже, не мигрируя базу.

**Установщик.** Порядок вопросов: язык, домен сервера, e-mail, режим доступа, режим и домен панели, способ
проверки ACME, masquerade. Режим доступа спрашивается раньше панели, потому что от него зависит, допустим ли
`server`. При `tunnel` вопрос о панели предлагает `subdomain` по умолчанию и `server` как вариант; при `public`
режим `server` недоступен, поэтому спрашивается только домен панели. Пустой ответ на вопрос о домене означает
`panel.<домен>`; если введённое совпало с этим значением, в базу пишется пустой `Domain`, чтобы панель
переезжала вместе с доменом сервера.

Флаги: `--panel-mode subdomain|server` и `--panel-domain ИМЯ`. По умолчанию `subdomain`. `--panel-domain` без
режима означает `subdomain`; `--panel-mode server` с другим `--panel-domain` — ошибка. Без терминала
действуют те же умолчания, поэтому существующие автоматические установки без новых флагов сохраняют прежний
адрес панели.

Перед установкой печатаются A-записи для домена сервера и, если он отличается, для домена панели. DNS не
проверяется блокирующе: запись могли создать только что, и установка не должна ждать распространения. При
HTTP-01 нужны обе записи и свободный порт 80; при DNS-01 провайдер должен уметь обе зоны. Итоговый блок
установщика печатает разрешённый адрес панели, а не жёстко заданный `panel.<домен>`.

**Интерфейс.** В настройках панели появляется домен панели и ссылка на неё; поля редактирования нет. В режиме
`tunnel` ссылка ведёт на `https://127.0.0.1:8443` после проброса порта, а домен показывается как имя
сертификата; браузер может предупредить, потому что ACME-сертификат выписан на домен, а не на петлю. В
публичном режиме ссылка строится по домену панели и порту 8443. Подсказки про сертификат перестают упоминать
`panel.<домен>` как единственный вариант.

**Отвергнутые варианты.** (1) Caddy и SNI, как у внешней панели, — лишняя служба и второй источник
сертификатов при другом транспорте. (2) Отдельный сертификат только для панели — расхождение с `pinSHA256` и
вторая учётная запись ACME. (3) Публичная панель на домене сервера — смешение ролей и лишняя видимость.
(4) Произвольный внешний домен панели — ломает один базовый домен и один ACME-провайдер; для этого нужна
отдельная задача. (5) Хранить только домен без режима — при смене домена сервера нельзя отличить «панель на
домене сервера» от «явно заданный домен, совпавший со старым». (6) Редактирование домена панели в интерфейсе
сейчас — расширяет объём на перевыпуск сертификата и обработку ошибок смены.
