# Сертификат панели: ACME, HTTP-01 по умолчанию и подмена на ходу

**Статус:** принято

Панель должна открываться по HTTPS на `panel.<домен>` с сертификатом, которому браузер верит без
предупреждений, и продлевать его сама. Сертификат нужен и ядру: клиенты Hysteria подключаются к `<домен>` с
`pinSHA256` из того же сертификата. Выпуск не должен требовать ручных шагов, а продление — остановки панели.

**Один сертификат на два имени.** Запрашиваются `<домен>` и `panel.<домен>` (если домен уже начинается с
`panel.`, второго имени нет). Отдельный сертификат только для панели сломал бы клиентов: ядро предъявляет
сертификат при подключении к `<домен>`, и имя в нём должно совпадать с SNI. Один сертификат на оба имени
устраняет и расхождение отпечатков: ключ клиента и панель всегда говорят об одном сертификате.

**Кто выпускает.** Панель, пакет `internal/certs`, поверх `golang.org/x/crypto/acme`. Внешний `certbot` не
используется: он потребовал бы отдельной службы, своего формата хранения и ещё одного способа продления.
`autocert` не взят потому, что его кэш — это каталог с именами по хешу, а панели нужны предсказуемые
`fullchain.pem` и `privkey.pem` по FHS и права 0600. `certmagic` и `lego` тянут целый набор DNS-провайдеров,
который в MVP не нужен.

**HTTP-01 по умолчанию.** На время выпуска панель занимает порт 80 и отдаёт ответ проверки по
`/.well-known/acme-challenge/<token>`. Порт берётся только на выпуск и отпускается после него; TCP-часть
masquerade на 80 по-прежнему отложена (ADR-0016). HTTP-01 не требует доступа к API DNS-провайдера и работает на
любом VPS, где домен уже указывает на сервер.

**DNS-01 как опция.** Для сервера за закрытым портом 80 или с доменом на чужом DNS способ проверки — `dns`.
Панель не тащит SDK каждого провайдера: встроенный Cloudflare-клиент использует только HTTP API, а для
остальных случаев остаётся внешняя программа-хук:
`хук present <имя> <значение>` и `хук cleanup <имя> <значение>`. Администратор сам решает, чем управлять зоной,
а обновление панели не добавляет зависимостей. Хук обязан быть исполняемым файлом, доступным пользователю
службы; проверка — до изменений в системе и ещё раз от имени службы.

**Cloudflare.** Первый встроенный провайдер выбран потому, что его API простой, а токен можно ограничить одной
зоной и правом `Zone.DNS Edit`. Для поиска зоны по имени нужен ещё `Zone.Zone Read`; если задан zone ID, хватает
только `Zone.DNS Edit`. Панель создаёт TXT-запись `_acme-challenge.<домен>` с TTL 120 секунд и удаляет её после
проверки или ошибки, если запись успела появиться. Токен передаётся установщику файлом (не аргументом командной строки), читается
командой `setup` и хранится в `appstate` вместе с настройками ACME; в журнал и интерфейс он не попадает. База
панели и её резервные копии содержат этот секрет, поэтому их нужно защищать как пароли.

**Выбор провайдера.** В настройках ACME есть `dns_provider`: `hook` или `cloudflare`. Пустое значение в базе
старой версии означает `hook` при наличии `dns_hook`; миграция не требуется. Провайдер и токен записываются
установщиком на пустой базе. На уже настроенной панели их меняет команда `hysteria-ward acme` при остановленной
службе: она открывает базу на запись, меняет только явно указанные поля и не печатает токен. Без флагов команда
показывает текущие настройки. Смена через браузерный API/UI не сделана: секрет не должен появляться в браузере
без отдельного решения о его защите. После записи службу нужно запустить снова — настройки ACME читаются при
старте.

**Ключ учётной записи.** Лежит рядом с сертификатом в `acme-account.key` (0600) и переиспользуется при
продлении. Новый ключ означал бы новую учётную запись ACME и её пределы.

**Подмена на ходу.** `certs.Manager` держит текущий сертификат и отдаёт его через `GetCertificate`. Панель
берёт сертификат при каждом рукопожатии, поэтому продление не требует её перезапуска. Ядро получает
сертификат из файлов при применении конфигурации; после успешного выпуска панель сама вызывает применение,
чтобы ядро подхватило новый файл. Продление разрывает активные соединения ядра на время его перезапуска — это
плата за то, что панель остаётся на месте. Смена сертификата не сбрасывает сессии администратора.

**Отпечаток для ключей.** Ключ `hysteria2://` собирается по текущему сертификату из `Manager`, а не по копии,
снятой при старте. После «Применить» сертификат перечитывается с диска. Поэтому `pinSHA256` в новом ключе
всегда указывает на тот сертификат, который предъявит ядро, а не на прежний.

**Смена домена.** Домен меняется из интерфейса, и прежний сертификат выписан на другие имена. После записи
домена панель будит выпуск, а фоновая проверка сравнивает имена в текущем сертификате с нужными: если хотя бы
одного не хватает, сертификат перевыпускается, не дожидаясь продления. Выпуск начинается сразу: иначе ключ,
собранный по прежнему сертификату, указывал бы на имя, которого в нём нет.

**Провал выпуска.** Панель не остаётся без входа: пока настоящего сертификата нет, она открывается с
самоподписанным и повторяет выпуск с нарастающей паузой (от минуты до часа). Причина видна в
`GET /api/certificate`, повтор запускается `POST /api/certificate/issue`. Установщик по-прежнему ставит drop-in
`serve --debug` до появления сертификата: без него на чистом сервере панель нечем запустить. После появления
файла drop-in снимается повторным запуском установщика.

**Права.** Сертификат и ключ пишутся атомарно (временный файл, затем переименование) с правами 0600; каталог
`/etc/hysteria-ward/certs` — 0700 и принадлежит службе. Временный файл удаляется и при ошибке.

**Настройки.** Способ проверки, адрес ACME-каталога, провайдер DNS и его секрет лежат в `appstate` ключом
`acme`; e-mail — отдельным ключом `acme_email`, как и раньше. Они записываются `setup` вместе с остальными
ответами; на уже настроенной панели — командой `acme`. Пустой адрес каталога означает Let's Encrypt; подмена
нужна для испытательного ACME и проверок.

**Отвергнутые варианты.** (1) Сертификат только для `panel.<домен>` — клиенты Hysteria остались бы без
подходящего имени. (2) Продление с остановкой панели — администратор терял бы вход на время выпуска, а
неудачная проверка оставляла бы его без панели. (3) Самоподписанный сертификат как рабочий — браузер
предупреждает, а `pinSHA256` в ключах не имеет смысла. (4) Раздавать сертификат только панели, а ядру оставлять
файл до следующего «Применить» — отпечаток в новых ключах разошёлся бы с ядром.
