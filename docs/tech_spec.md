1. Общие сведения и цели проекта

1.1. Наименование и назначение системы

Паспорт проекта:

Параметр	Значение спецификации
Идентификатор системы	hysteria2-manager
Полное наименование	Веб-менеджер и демонизированная служба управления туннелями Hysteria 2
Тип программного обеспечения	Автономная управляющая служба (системный демон) со встроенным веб-интерфейсом
Целевые платформы	Встроенные сетевые маршрутизаторы Keenetic и OpenWrt (среда Entware / OPKG), а также серверные дистрибутивы Linux VPS/VDS. Референс приёмки — Keenetic Ultra KN-1811 (aarch64, Entware на USB)

Служба hysteria2-manager представляет собой специализированное программное обеспечение, предназначенное для автоматизации процессов конфигурации, жизненного цикла (запуск, остановка, перезапуск), генерации криптографических сертификатов, визуального мониторинга и управления P2P-соединениями протокола Hysteria 2 (включая технологию Hysteria Realms).

1.2. Цели разработки и ключевая область применения

Основными техническими и эксплуатационными целями проекта являются:

1. Исключение необходимости работы администратора через интерфейс командной строки (CLI) и ручной правки YAML-конфигураций при развертывании и обслуживании Hysteria 2.
2. Обеспечение сплошного управления экземплярами Hysteria 2 в режимах server и client через единый графический веб-интерфейс, оптимизированный для работы на любых типах устройств.
3. Гарантия работы в условиях жестких аппаратных ограничений (низкое потребление ОЗУ, минимальная нагрузка на CPU) встроенных устройств под управлением операционных систем KeeneticOS и OpenWrt с использованием пакетов Entware.
4. Предоставление средств обхода сложных топологий NAT (включая CGNAT и мобильные операторы) без применения публичных IPv4-адресов на базе встроенной поддержки протокола Hysteria Realms (P2P NAT Traversal).

1.3. Совместимость с протоколом Hysteria 2 и Hysteria Realms

Продукт должен обеспечивать полную интеграцию со спецификациями протокола Hysteria 2:

* Транспорт QUIC / HTTP/3: Эксплуатация модифицированного стека QUIC, маскирующего прокси-трафик под легитимный обмен данными по протоколу HTTP/3 для предотвращения сигнатурного детектирования и активного зондирования системами DPI.
* Маскировка обфускацией (obfs): Поддержка механизмов обфускации (включая алгоритм Salamander) для превращения QUIC-пакетов в криптографически неотличимый от случайного шум.
* Динамический ротация портов (Port Hopping): Управление интервалами портов на стороне сервера и клиента для противодействия блокировкам по кортежу IP:Port со стороны провайдера.
* Списки контроля доступа (ACL): Формирование и динамическое применение правил фильтрации, маршрутизации и прямого пропускного режима (direct/proxy/reject) на основе списков ACL.
* P2P NAT Traversal (Hysteria Realms): Полноценная поддержка технологии Hysteria Realms, обеспечивающей установление прямого peer-to-peer соединение между клиентом и сервером за NAT (включая двойной NAT и CGNAT) с применением техники UDP hole punching и промежуточных серверов рандеву (rendezvous).

2. Архитектура и стек технологий

2.1. Backend и сетевой слой (Golang)

Служба бэкенда проектируется на языке Go и компилируется в единый монолитный бинарник.

Компонент бэкенда	Технология/Архитектура	Требования и назначение
Системный демон	Go (Golang)	Сборка единого статически скомпилированного исполняемого файла под ARM64 (aarch64) и x86_64. Объем потребления ОЗУ в простое фиксируется по факту замера на референсном устройстве после MVP: публичного эталона такого норматива не существует, а ключ `-ldflags "-s -w"` уменьшает размер файла, а не потребление памяти.
Сетевой API	REST API над HTTP/2	Обработка управляющих команд UI (управление процессами Hysteria 2, генерация сертификатов, манипуляция конфигурациями, авторизация).
Канал динамических данных	WebSocket (RFC 6455) / SSE (Server-Sent Events)	Передача потоковых данных метрик скорости, сетевого статуса и системных событий в режиме реального времени с минимальным оверхедом. На участке демон → браузер используется SSE; метрики собираются опросом, поскольку ядро Hysteria 2 не имеет push-канала.

2.2. Frontend и UI-компоненты (Svelte/SvelteKit + Tailwind CSS)

Интерфейс пользователя реализуется на современном реактивном веб-стеке:

* Фреймворк и язык: Svelte + Vite (режим SPA) со строго типизированным TypeScript. Серверный слой SvelteKit не используется как избыточный для встраиваемого приложения.
* Стилизация и адаптивность: Tailwind CSS для верстки интерфейса под мобильные и десктопные разрешения.
* Сборка и встраивание:
  * Готовый артефакт компиляции фронтенда (HTML/JS/CSS) встраивается непосредственно в тело Go-бинарника с помощью директивы go:embed.
  * Приложение не должно требовать внешних веб-серверов (Nginx, Lighttpd, Apache) или внешних интерпретаторов (Node.js).

2.3. Хранение данных (SQLite / bbolt)

Для локального сохранения состояний, параметров UI, учетных данных администратора, TLS-ключей и агрегированных статистических метрик должно использоваться встраиваемое transactional key-value хранилище bbolt (ADR-0002). Выбор обусловлен необходимостью устранения внешних системных зависимостей, нулевыми затратами на межпроцессное взаимодействие (IPC), стойкостью к внезапным отключениям питания на встроенных устройствах и отсутствием cgo: драйверы SQLite либо требуют cgo и ломают статическую сборку, либо не поддерживают целевые архитектуры.

3. Функциональные требования

3.1. Модуль конфигураций Hysteria 2 (Сервер и Клиент)

Модуль должен обеспечивать валидацию, генерацию и визуальное редактирование YAML-конфигураций для ролей server и client с точным соответствием структуре параметров Hysteria 2.

Ключ в структуре YAML Hysteria 2	Элемент интерфейса UI	Требования и допустимый диапазон значений
listen / server	Текстовое поле ввода адреса	Формат host:port для классических подключений либо realm:// / realm+http:// для P2P-режима.
auth.type / auth.password	Выпадающий список / Селектор	Вариант password с полем текстового ввода или встроенным генератором криптостойких паролей.
bandwidth.up / bandwidth.down	Числовые поля с выбором единиц (Mbps/Kbps)	Ограничение пропускной способности (например, 100 mbps).

tls.sni	Текстовое поле ввода SNI	Переопределение имени SNI при клиентских подключениях.
tls.pinSHA256	Текстовое поле хэша	Валидация публичного ключа сервера (256-битный SHA256-хэш Base64/Hex).

3.2. Модуль TLS-сертификатов и безопасности

Система должна реализовывать три ключевых сценария конфигурации TLS-слоя:

1. Самоподписанные сертификаты (hysteria cert):
  * Автоматический вызов встроенной генерации пары сертификат/ключ.
  * Вычисление хэша pinSHA256 для автоматического встраивания в конфигурации клиентов.
  * Технический нюанс Realms: При работе сервера в режиме Hysteria Realms с самоподписанным сертификатом, во избежание ошибки клиентов tls: internal error (вызываемой расхождением SNI при прямолинейном P2P-подключении по IP-адресу), модуль обязан принудительно прописывать директиву sniGuard: disable в секцию tls конфигурационного файла сервера:

tls:
  cert: /opt/etc/hysteria2-manager/certs/server.crt
  key: /opt/etc/hysteria2-manager/certs/server.key
  sniGuard: disable


2. Получение доверенных сертификатов ACME DNS-01 (реализуется на этапе 4, после MVP: требует внешнего DNS-провайдера и доступа в интернет):
  * Интеграция с ACME-клиентом для автоматического прохождения DNS-01 challenge (для серверов без публичного IP или за NAT).
3. Ручная загрузка и SNI Override:
  * Поддержка пользовательских сертификатов (.crt/.key) и возможность явного переопределения tls.sni на стороне клиента.

3.3. Модуль P2P NAT Traversal (Hysteria Realms)

Для обеспечения связи в условиях отсутствия публичного IP-адреса и проброса портов модуль должен реализовывать обработку Hysteria Realms (реализуется на этапе 3, после базового сервера):

Синтаксис адресации и параметры URI

Служба должна валидировать и формировать URI структуры: realm://<token>@<rendezvous-host>[:port]/<realm-name>[?query_params]

* realm:// — основной безопасный транспорт (HTTPS / порт 443).
* realm+http:// — открытый транспорт для отладочных сред (HTTP / порт 80).
* <token> — авторизационный токен сервера рандеву.
* <realm-name> — уникальное имя области (6–64 символов, буквы, цифры, -, _).
* Поддерживаемые query-параметры:
  * ?stun=<host:port> — переопределение STUN-сервера (допускается повторное указание нескольких параметров для передачи массива STUN-серверов).
  * ?lport=<1-65535> — привязка локального UDP-сокета к фиксированному порту для статической настройки сопоставления (NAT mapping).

Инфраструктура Rendezvous и STUN

* Поддержка публичной сети рандеву: realm://public@realm.hy2.io/<realm-name>.
* Возможность указывать self-hosted серверы рандеву (apernet/hysteria-realm-server).
* Дефолтный список STUN-серверов:
  * stun.nextcloud.com:3478
  * stun.sip.us:3478
  * global.stun.twilio.com:3478

Матрица совместимости типов NAT (NAT Compatibility Matrix)

Модуль обязан учитывать физические ограничения пробития NAT при установлении P2P-сессий:

Тип NAT стороны A / B	Public IP	Full Cone	Restricted / Port-Restricted	Sym (predictable)	Sym (random)
Public IP	✅	✅	✅	✅	✅
Full Cone	✅	✅	✅	✅	✅
Restricted / Port-Restricted	✅	✅	✅	⚠️	❌
Sym (predictable)	✅	✅	⚠️	⚠️	❌
Sym (random)	✅	✅	❌	❌	❌

Обозначения: ✅ — стабильное установление P2P-туннеля; ⚠️ — вероятностное установление (зависит от эвристики предсказания портов); ❌ — физически невозможное прямое соединение.

Техническое обоснование эвристики: Для успешного пробития в случаях Sym (predictable) алгоритму Hysteria требуется минимум 2 рефлексивных порта в одной группе с шагом приращения не более 4 (port allocation delta) рефлексивного транспортного адреса NAT. Три STUN-сервера — рекомендуемое значение по умолчанию, а не жёсткий порог; при одном STUN-сервере эвристика действительно перестаёт работать.

3.4. Модуль мониторинга, статистики и лимитов

* Интеграция с API: Взаимодействие с Hysteria 2 Traffic Stats API через локальный Unix-сокет или REST-эндпоинт core-процесса.
* Метрики в реальном времени: Измерение текущей входящей (Rx) и исходящей (Tx) скорости с частотой обновления 1 секунда.
* Агрегированная история трафика: Построение и отображение графиков нагрузки с дискретизацией за фиксированные временные интервалы:
  * 1 час: шаг агрегации 5 секунд.
  * 3 часа: шаг агрегации 15 секунд.
  * 24 часа: шаг агрегации 1 минута.
* Учет лимитов трафика: Фиксация суммарных объемов за период, отслеживание лимитов клиентов и автоматическое отключение конкретного пользователя при превышении установленной квоты (без остановки всего экземпляра).

Разделы интерфейса

* Settings & TLS: Управление сертификатами, паролями доступа к UI и параметрами демона.

4.2. Интеграция и шеринг конфигураций (QR-коды и URI)

Для быстрой передачи настроек в клиентские приложения (v2rayNG, Nekobox, Hysteria CLI и др.) веб-интерфейс должен генерировать:

* Канонические ссылки форматов hysteria2:// и сокращенного hy2:// с запеканием всех параметров аутентификации, SNI, obfs и pinSHA256 в URI query.
* Векторные и растровые QR-коды для мгновенного сканирования мобильными устройствами.

4.3. Авторизация и защита данных

* Сессионная защита: пароль администратора по умолчанию не задан и включается вручную (ADR-0004, осознанно принятый риск). При включённом пароле — форма входа по мастер-паролю; выдаётся cryptographically secure HTTP-only cookie с ограничением времени жизни.
* Защита секретов: Приватные ключи TLS (key), токены Realms и пароли клиентов должны храниться в базе данных SQLite/bbolt с ограничением прав доступа на уровне файловой системы.

5. Требования к дистрибуции и развертыванию

5.1. Пакетная сборка для роутеров (OPKG / Entware)

Для платформ Keenetic и OpenWrt формируется пакет формата .ipk.

Структура каталогов и права доступа

* /opt/etc/hysteria2-manager/hysteria2-manager — бинарный файл (права 0755, owner root:root).
* /opt/etc/hysteria2-manager/data/ — база данных и конфиги (права 0640, owner root:root).
* /opt/etc/hysteria2-manager/certs/ — TLS-сертификаты и ключи (права 0600, owner root:root).

Скрипт инициализации /opt/etc/init.d/S99hysteria2-manager

Скрипт должен следовать контракту init-системы Entware (`rc.func` / `rc.unslung`), а не `rc.common` из OpenWrt, и поддерживать следующий набор команд:

* start — запуск демона с проверкой наличия PID-файла.
* stop — корректное завершение процесса (SIGTERM, затем SIGKILL через 5 сек).
* restart — последовательный вызов stop и start.
* status — проверка статуса процесса по PID и возвращение стандартных кодов завершения (0 — работает, 3 — остановлен).
* check — валидация целостности конфигурации и доступности базы данных.

5.2. Скрипты автоматической установки (Bash)

Установка осуществляется универсальным сценарием install.sh, который скачивает релизные бинарники из GitHub Releases. Скрипт обязан выполнять автоматический фоллбэк при отсутствии curl:

#!/bin/sh
# Универсальный командный скрипт установки hysteria2-manager
set -e

REPO_URL="https://github.com/<owner>/hysteria-ward/releases/latest/download/install.sh"

if command -v curl >/dev/null 2>&1; then
    echo "[INFO] Использование curl для загрузки дистрибутива..."
    curl -sL "$REPO_URL" | sh
elif command -v wget >/dev/null 2>&1; then
    echo "[INFO] curl не найден. Использование встроенного busybox wget..."
    wget -qO- "$REPO_URL" | sh
else
    echo "[ERROR] Ни curl, ни wget не найдены в системе." >&2
    exit 1
fi
